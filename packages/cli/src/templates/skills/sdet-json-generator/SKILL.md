# Markdown Testcases to JSON Transformer

Converts markdown-formatted test cases into JSON test suites that conform to `testsuite.schema.json`,
enabling execution in automated testing frameworks like plyson.

---

## When to Use

- Converting markdown testcase documentation into executable JSON test suites
- Preparing test cases for API automation frameworks
- Reusing common global test cases (auth flows, setup steps) across multiple test suites
- Validating test cases against schema before execution
- Transforming markdown stories/requirements into structured test definitions

---

## Input

One of the following:

1. **Markdown testcase file** — A `.md` file containing structured testcases (typically generated by the sdet-testcase-generator skill)
2. **Inline markdown** — Testcase markdown pasted directly in the chat
3. **Project context** — Optional reference to project.json to identify reusable global testcases

### Expected Markdown Format

Each testcase should follow this structure:

```
### TC_<ID>: <Title>

**Type:** positive / negative / boundary / security / integration
**Priority:** P0 / P1 / P2
**Layer:** API / Unit / Integration / UI
**AC Reference:** AC-X

**Pre-condition:**
<State or setup required before test>

**Steps:**
1. <HTTP Method> <endpoint> with <request details>
2. <Additional steps if needed>

**Expected Result:**
<Status code, response body, or system state verification>

**Assertion:**
<Automation assertion logic>
```

### Optional: Swagger/OpenAPI Spec

Provide a link to the OpenAPI/Swagger specification for:

- Automatic endpoint validation
- Request/response schema inference
- Auto-fill payload generation

## Step 1 — Analyze Markdown Testcases

Extract and normalize test case metadata:

| Metadata         | Source                       | Usage                                          |
| ---------------- | ---------------------------- | ---------------------------------------------- |
| **Test ID**      | TC\_<ID> in title            | Becomes `id` in JSON                           |
| **Title**        | Markdown heading             | Becomes `title` in JSON                        |
| **Type**         | `**Type:**` field            | Maps to `testType: [positive\|negative\|edge]` |
| **Precondition** | `**Pre-condition:**` section | Guides step assembly and variable extraction   |
| **Steps**        | `**Steps:**` list            | Transforms to HTTP request definitions         |
| **Assertions**   | `**Assertion:**` section     | Converts to response validations               |

### Example transformation

**Markdown input:**

```
### TC_AUTH01_003: Registration rejected when email format is invalid → 400

**Pre-condition:** No pre-condition needed.

**Steps:**
1. POST /auth/register with email=`invalid-email`
2. Include firstname, lastname, password with valid values

**Expected Result:** 400 Bad Request with validation error

**Assertion:** response.status == 400 AND errors array contains {field: "email"}
```

**JSON output** (partial):

```json
{
  "id": "TC_AUTH01_003",
  "title": "Registration rejected when email format is invalid → 400",
  "testType": "negative",
  "steps": [
    {
      "title": "POST /auth/register with invalid email",
      "request": {
        "method": "POST",
        "endpoint": "/auth/register",
        "payload": {
          "email": "invalid-email",
          "firstname": "<firstname>",
          "lastname": "<lastname>",
          "password": "<password>"
        }
      },
      "response": {
        "validations": {
          "statusCode": 400,
          "assertions": [...]
        }
      }
    }
  ]
}
```

## Step 2 — Extract and Note Preconditions

For each testcase, analyze the **Pre-condition** field:

### Precondition Types

| Category                | Example                           | Action                                                    |
| ----------------------- | --------------------------------- | --------------------------------------------------------- |
| **Authentication**      | "User logged in with valid token" | Check project.json for `TC_USER_AUTH` or similar          |
| **Data setup**          | "User exists in database"         | Extract as suite-level `beforeAll` or test-level variable |
| **System state**        | "Service is available"            | No action; standard assumption                            |
| **External dependency** | "Cart contains 3 items"           | Extract as variable or chain from prior step              |

### Decision Tree

```
For each precondition:
├─ Is this a GLOBAL reusable flow? (e.g., login, registration)
│  └─ YES: Check project.json for matching global testcase reference
│     ├─ Found: Add as `{ ref: "TC_ADMIN_AUTH" }` to beforeAll/steps
│     └─ Not found: Create as suite-level beforeAll step
├─ Is this a DATA setup? (e.g., cart has items, user exists)
│  └─ YES: Extract as variable or inlinePayload in the step
└─ Is this a STATE assumption? (e.g., service is available)
   └─ NO ACTION: Assume it in test environment
```

## Step 3 — Check project.json for Global Testcases

Load [project.json](./references/project-json-structure.md) and identify reusable testcases in the `beforeAll` array:

```json
{
  "title": "Marketplace API Validation",
  "beforeAll": [{ "ref": "TC_ADMIN_AUTH" }, { "ref": "TC_USER_AUTH" }]
}
```

### Reuse Strategy

For each testcase precondition:

1. **If precondition mentions authentication:**
   - Check if `TC_ADMIN_AUTH` or `TC_USER_AUTH` exists in project.json
   - If found: Add `{ "ref": "TC_ADMIN_AUTH" }` to the test's steps or suite's beforeAll
   - If not found: Create the auth step inline

2. **If precondition mentions data setup:**
   - Check if a matching global testcase ID exists (e.g., TC_SETUP_CART)
   - If yes: Reference it; otherwise, define setup as variables or inline step

3. **If precondition is generic** (e.g., "service available"):
   - No action needed; assume it's satisfied in test environment

## Step 4 — Generate Common Suite-Level Steps

If multiple testcases share the same precondition and no global testcase exists:

Create a suite-level `beforeAll` step instead of duplicating in each testcase:

**Before (duplicated in each testcase):**

```json
"testCases": [
  {
    "steps": [
      { "title": "Login as admin", "request": {...} },
      { "title": "Create product", "request": {...} }
    ]
  },
  {
    "steps": [
      { "title": "Login as admin", "request": {...} },
      { "title": "Delete product", "request": {...} }
    ]
  }
]
```

**After (suite-level reuse):**

```json
{
  "beforeAll": [
    { "ref": "TC_ADMIN_AUTH" }
  ],
  "testCases": [
    {
      "steps": [
        { "title": "Create product", "request": {...} }
      ]
    },
    {
      "steps": [
        { "title": "Delete product", "request": {...} }
      ]
    }
  ]
}
```

## Step 5 — Transform to JSON Schema

Map each markdown testcase to the JSON structure defined in `testsuite.schema.json`:

### Key transformations

| Markdown Field                    | JSON Path                                 | Notes                                    |
| --------------------------------- | ----------------------------------------- | ---------------------------------------- |
| Test ID                           | `testCases[].id`                          | Unique identifier                        |
| Title                             | `testCases[].title`                       | Human-readable name                      |
| Type (positive/negative/boundary) | `testCases[].testType`                    | Enum: "positive" \| "negative" \| "edge" |
| Pre-condition                     | `beforeAll` (suite) or inline variable    | Reuse global testcases where possible    |
| HTTP Method + Endpoint            | `steps[].request.method`, `.endpoint`     | Extract from Steps markdown              |
| Request Payload                   | `steps[].request.payload`                 | From markdown step details               |
| Expected Status                   | `steps[].response.validations.statusCode` | HTTP status code(s)                      |
| Assertions                        | `steps[].response.validations.assertions` | Array of validation rules                |
| Assertion Operators               | `assertions[].operator`                   | Must match testsuite.schema.json enum    |

### Assertion Operator Mapping

Convert markdown assertions to schema operators:

| Markdown assertion            | Schema operator                         |
| ----------------------------- | --------------------------------------- |
| `response.status == 200`      | `statusCode: 200`                       |
| `errors array contains {...}` | `operator: "contains"`                  |
| `field exists`                | `operator: "exists"`                    |
| `field is not null`           | `operator: "isNotNull"`                 |
| `length > 5`                  | `operator: "hasMinLength", value: 6`    |
| `matches pattern /regex/`     | `operator: "matches", value: "/regex/"` |

## Step 6 — Validate Schema Compliance

After generating JSON:

1. **Load testsuite.schema.json** — The official schema file
2. **Validate each testcase** against required fields:
   ```json
   Required: ["id", "title", "tags", "steps"]
   ```
3. **Validate each step** against request/response structure
4. **Check operator enums** — All assertion operators must match schema
5. **Report errors** — List any schema violations with line numbers and suggested fixes

### Validation Checklist

- [ ] Every testcase has `id`, `title`, `tags`, `steps`
- [ ] Every step has `title`, `request` (with `method`, `endpoint`), and `response` (with `validations.statusCode`)
- [ ] All assertion operators are valid enum values from schema
- [ ] All HTTP methods are uppercase: GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS
- [ ] Status codes are numbers, not strings
- [ ] Payload fields match OpenAPI schema (if provided)
- [ ] All referenced global testcases (via `ref`) exist in project.json
- [ ] No circular dependencies in beforeAll references

### Example Error Report

```
❌ Schema validation failed:

File: Auth.testsuite.json
Line 45, testCase "TC_AUTH02_005":
  - Missing required field: "tags"
  - Suggestion: Add tags array, e.g., ["authentication", "negative"]

Line 52, step "Login with invalid credentials":
  - Invalid operator "doesNotEqual" in assertion[0]
  - Valid operators: "equals", "notEquals", "exists", "contains", ... (see schema)
  - Suggestion: Change to "notEquals"

✓ Fix errors and re-validate.
```

## Step 7 — Output and File Organization

### Output Structure

Generate JSON files and save to the default location:

```
suites/
├── <Suite-Name>.testsuite.json
├── <Feature-Name>.testsuite.json
└── ...
```

Example:

```
suites/
├── Auth.testsuite.json
├── Product.testsuite.json
└── Cart.testsuite.json
```

### File Naming Convention

```
<Feature-or-Story-Name>.testsuite.json
```

Use the story title or feature area as the file name. Examples:

- `Auth.testsuite.json` — All authentication testcases
- `UserManagement.testsuite.json` — User-related testcases
- `ProductCatalog.testsuite.json` — Product catalog testcases

### Metadata at Suite Level

Each generated JSON file should include suite-level metadata:

```json
{
  "$schema": "./node_modules/@plyson/test/src/schemas/project.schema.json",
  "title": "Authentication Tests",
  "description": "API validation tests for user authentication flows",
  "disabled": false,
  "tags": ["authentication", "api", "critical"],
  "variables": {},
  "beforeAll": [
    { "ref": "TC_ADMIN_AUTH" }
  ],
  "testCases": [...]
}
```

## Complete Workflow Example

### Input: Markdown testcase

```markdown
## AUTH-01 — User Registration

### TC_AUTH01_001: User registered successfully with valid data → 201

**Type:** positive
**Priority:** P0
**Layer:** API
**AC Reference:** AC-1

**Pre-condition:** No pre-condition needed.

**Steps:**

1. POST /auth/register with email=`user@example.com`, firstname=`John`, lastname=`Doe`, password=`SecurePass123`

**Expected Result:** 201 Created. Response contains userId, email, role.

**Assertion:** response.status == 201 AND response.body.email == user@example.com AND response.body.role == "USER"

---

### TC_AUTH01_002: Registration fails with invalid email → 400

**Type:** negative
**Priority:** P0
**Layer:** API
**AC Reference:** AC-2

**Pre-condition:** No pre-condition needed.

**Steps:**

1. POST /auth/register with email=`not-an-email`, firstname=`John`, lastname=`Doe`, password=`SecurePass123`

**Expected Result:** 400 Bad Request. Response contains validation error.

**Assertion:** response.status == 400 AND errors array contains {field: "email"}
```

### Processing Steps

1. **Extract testcase IDs:** `TC_AUTH01_001`, `TC_AUTH01_002`
2. **Analyze preconditions:** Both have "No pre-condition" → No beforeAll needed
3. **Check project.json:** No referenced global testcases
4. **Transform to JSON:** Map steps to request/response schema
5. **Validate schema:** All assertions use valid operators
6. **Output file:** `suites/Auth.testsuite.json`

## Key Principles

1. **Reuse global testcases** — Always check project.json before creating duplicate auth/setup flows
2. **Extract and name preconditions** — Document what each test assumes
3. **Use suite-level beforeAll** — Reduce duplication when multiple tests share setup
4. **Schema validation is non-negotiable** — Never skip the final validation step
5. **Keep step titles atomic** — One clear action per step, parameterized where possible
6. **Map assertions precisely** — Every markdown assertion becomes a JSON validation rule

---

## Troubleshooting

| Issue                                                         | Solution                                                                          |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| "Schema validation failed: Missing field 'tags'"              | Add `tags` array to each testcase (e.g., `["positive", "authentication"]`)        |
| "Unknown operator 'doesNotEqual'"                             | Use valid operator from schema: `notEquals` (no "do" prefix)                      |
| "Referenced testcase TC_ADMIN_AUTH not found in project.json" | Create the global testcase first, or define auth as a suite-level beforeAll step  |
| "Endpoint validation failed against OpenAPI schema"           | Provide valid OpenAPI spec URL; endpoint must match spec exactly (case-sensitive) |
| "Duplicate testcase IDs"                                      | Ensure each testcase has a unique ID (TC*<FEATURE>*<NNN>)                         |
